Recruiter Backend
API and Flow Contract

Single backend handoff for recruiter signup, email verification, organization review, login, recruiter workspace APIs, candidate access, credit purchases, invoices, and hospital profile management.

Proposed contract — backend team to confirm

1. Scope and Flow Overview

1. RegisterCreate recruiter and organization; email verification is required.
2. Verify emailConsume registration code; keep organization review separate.
3. Sign inReturn authenticated recruiter session and organization status.
4. Organization reviewPending/rejected accounts cannot read recruiter resources.
5. Approved workspaceCheck existing job posts; post openings; search candidates, shortlist, unlock, manage credits/profile.
6. PaymentsHosted checkout; verified provider webhook records payment and credits.

This contract includes recruiter authentication and recruiter workspace data. Shared candidate authentication is outside scope. Frontend route guards are for navigation only; the backend is the authorization boundary.

3. Recruiter Registration

POST/auth/register

{
  "role": "recruiter",
  "fullName": "Rahul Menon",
  "email": "rahul@hospital.com",
  "phone": "+919876543210",
  "designation": "HR Manager",
  "organizationName": "MedCare Hospital",
  "organizationWebsite": "https://hospital.com",
  "city": "Chennai",
  "state": "Tamil Nadu",
  "password": "ExamplePassword@123",
  "termsAccepted": true
}

The current UI collects a ten-digit phone number and prepends +91. Confirm whether country code must be selectable. Password confirmation is checked in browser and is not sent.

Backend behavior: Validate all fields; normalize email; create recruiter and organization with email unverified and verification status pending; send registration OTP; return 201 Created. Do not grant recruiter workspace access at registration.

{
  "message": "Verification code sent",
  "userId": "user_123",

}

4. Email Verification and Resend

POST/auth/verify-code

{ "email": "rahul@hospital.com", "code": "482916", "purpose": "registration" }

On success, consume the one-time code and mark the email verified. This must not approve the organization.

{
  "verified": true,
  "purpose": "registration",
  "user": {
    "id": "user_123",
    "role": "recruiter",
    "email": "rahul@hospital.com",
    "emailVerified": true,
    "organizationVerificationStatus": "pending"
  }
}

POST/auth/resend-code

{ "email": "rahul@hospital.com", "purpose": "registration" }

OTP is six numeric digits, expires in about 10 minutes, single-use, and invalidated after success. Rate-limit by account and IP (suggested resend cooldown 60 seconds), and limit verification attempts.

POST/auth/login

{ "email": "rahul@hospital.com", "password": "ExamplePassword@123", "rememberMe": true }

rememberMe is a session-duration preference, not a user profile field. Successful login returns session information and the current authoritative organization status.

6. Password Recovery

Use shared auth endpoints while preserving recruiter context in the UI. Do not reveal whether the email exists.

POST/auth/forgot-password

{ "email": "rahul@hospital.com" }

Return generic 202 Accepted for both known and unknown emails.

POST/auth/verify-code

{ "email": "rahul@hospital.com", "code": "482916", "purpose": "password_reset" }

On success return a short-lived, single-use reset token. Keep this purpose distinct from registration verification.

POST/auth/reset-password

{ "email": "rahul@hospital.com", "resetToken": "reset-token-value", "newPassword": "NewExamplePassword@123" }

Invalidate reset token and revoke sessions according to security policy. Confirmation password is frontend-only.

7. Recruiter Workspace API

Every route in this section requires an approved recruiter access token:

Authorization: Bearer <accessToken>
Accept: application/json
Content-Type: application/json

Return 403 ORGANIZATION_NOT_APPROVED for pending/rejected organizations. Derive the organization from token claims or server-side session.

GET/recruiter/dashboard

{
  "metrics": { "candidateSearches": 284, "profilesUnlocked": 47,
    "shortlistedCandidates": 23, "availableCredits": 156 },
  "organization": { "name": "MedCare Hospital", "location": "Chennai, IN",
    "verificationStatus": "approved" },
  "recentActivity": [
    { "id": "act_01", "description": "Candidate profile unlocked",
      "occurredAt": "2026-09-24T09:00:00Z" }
  ],
  "recommendedCandidates": []
}

Recommended profiles must follow the masking rules below.

GET/recruiter/jobs

List jobs posted by the authenticated recruiter’s organization. Query parameters: page, pageSize, and optionally status. Return the common list envelope, including an empty items array and zero totals when the account has no postings. Each item includes id, title, specialty, location, employmentType, optional salaryRange, description, requirements (string array), status, postedAt, and optional updatedAt.

After approved recruiter login, the frontend calls this endpoint: a non-empty result routes to /recruiter/dashboard; no jobs routes to /recruiter/jobs to create the first opening. If this check fails, login continues to the dashboard and the Job Postings page displays its own error. Scope results to the authenticated organization; do not use a client-supplied organization ID.

POST/recruiter/jobs

{
  "title": "Registered Nurse - Critical Care",
  "specialty": "Critical Care",
  "location": "Chennai, Tamil Nadu",
  "employmentType": "Full-time",
  "salaryRange": "₹8,00,000–₹12,00,000 / year",
  "description": "Provide direct care to patients in the critical care unit.",
  "requirements": ["Active state nursing license", "Two years of ICU experience"]
}

salaryRange is optional; current form requires the other fields. Validate and trim values, enforce length limits, validate employment type, and sanitize rendered text. Enforce the organization’s job-post plan/entitlement on the server. Create the posting under the authenticated organization, set postedAt, initialize status to published (or return the moderation state), and return 201 Created with the created job object.

Return 422 VALIDATION_ERROR with field errors for invalid values and 409 JOB_POST_LIMIT_REACHED when the account has reached its entitlement. Do not create a record on either failure. This initial frontend supports listing and creating; update/close/delete actions are not exposed.

GET/recruiter/candidates

Query: query, specialty, location, minExperience, maxExperience, licenseState, employment, availability, page, pageSize.

Return the common list envelope. Search item:

{ "id":"MH-10482", "initials":"MH", "title":"Registered Nurse",
  "specialty":"Critical Care", "experience":"5 Years Experience",
  "experienceYears":5, "location":"Chicago, IL", "education":"BSN",
  "license":"Active License - IL", "availability":"Immediate",
  "employment":"Full-time", "tags":["ICU","BLS","ACLS"], "unlocked":false }

Search results must not return full name, personal email, phone, address, resume URL, or other private profile details before access is unlocked.

GET/recruiter/candidates/{candidateId}

Return candidate summary, profile sections, access state, and credit balance. Contact fields remain null/masked until the organization has unlocked that candidate.

{ "candidate": {}, "profile": { "summary":"...", "workExperience":[],
  "skills":[], "career":[], "contact": { "fullName":null, "email":null,
    "phone":null, "address":null } },
  "access": { "unlocked":false, "unlockCost":5 },
  "creditBalance": { "available":156 } }

POST/recruiter/candidates/{candidateId}/unlock

Request: {}
Response: { "candidateId":"MH-10482", "unlocked":true, "creditsUsed":5,
  "creditBalance": { "available":151 }, "profile": {} }

Atomically verify current organization approval and balance, debit once, record purchase, and grant access. Support an Idempotency-Key header so safe retries cannot double-charge. Return 409 INSUFFICIENT_CREDITS with no debit when balance is low.

GET/recruiter/purchased-candidates

Query: query, specialty, location, status, page, pageSize. Return common list envelope. Each result belongs to this organization and includes id, initials, name, title, specialty, experience, location, unlockedDate, status (Active/Contacted). Only expose resume/contact access after purchase; deliver downloads with an authorized short-lived URL.

GET/recruiter/shortlisted-candidates

Query: query, specialty, unlockStatus, location, page, pageSize. Return common list envelope. Candidate name stays masked while locked.

POST/recruiter/shortlisted-candidates

{ "candidateId":"MH-10482" }

Return 201 (or 200 if already saved): { "candidateId":"MH-10482", "shortlisted":true }.

DELETE/recruiter/shortlisted-candidates/{candidateId}

Return 204 No Content. Remove only the shortlist association; never delete the candidate or unlock purchase.

GET/recruiter/plans

Return { "plans": [], "currentPlan": {} }. Plan fields: id, name, price, currency, billingInterval, credits, jobPosts, recruiterSeats, validityDays, features. Server is authoritative for price and entitlements.

GET/recruiter/credits

{ "available":156, "used":94, "currency":"USD" }

8. Checkout, Payment, and Invoice

Payment security: Do not send raw card number, expiry, or CVV to MedHire API. Use provider-hosted checkout or provider tokenization. A browser redirect must never mark a payment successful or add credits.

POST/recruiter/checkout

{ "planId":"professional",
  "successUrl":"https://app.example.com/recruiter/payment-success",
  "cancelUrl":"https://app.example.com/recruiter/payment-failed" }

Return 201 Created with provider session and redirect URL:

{ "checkoutSessionId":"cs_123",
  "checkoutUrl":"https://payment-provider.example/session/cs_123" }

Validate plan and price server-side. A verified provider webhook is the source of truth for transaction status and credit grant. Use idempotent webhook handling; failed/cancelled checkout leaves balance unchanged.

GET/recruiter/checkout/{checkoutSessionId}

Return the authenticated organization's server-verified checkout status: pending, successful, failed, or cancelled. Return transaction ID and safe user-facing message when available. Scope the session to the owning organization. Update success only from a verified payment provider webhook, never from the browser redirect.

GET/recruiter/payment-history

Query: status (Successful/Failed/Pending), startDate, endDate, page, pageSize. Return common list envelope.

{ "id":"TXN-2026-09187", "date":"2026-09-18T00:00:00Z",
  "plan":"Professional", "credits":50, "amount":"268.92", "currency":"USD",
  "method":"Visa ending in 4242", "status":"Successful",
  "invoiceAvailable":true }

GET/recruiter/payment-history/{transactionId}/invoice

Authorize transaction ownership and invoice eligibility. Return invoice details or a short-lived authorized PDF URL/stream. Never expose public permanent invoice URLs.

{ "invoice": { "invoiceNumber":"INV-2026-1001", "date":"2026-09-18",
  "billedTo":{}, "billedFrom":{}, "lineItems":[], "subtotal":"250.00",
  "tax":"18.92", "total":"268.92", "currency":"USD",
  "transactionId":"TXN-2026-09187", "paymentMethod":"Visa ending in 4242",

  "registrationNumber":"REG-123", "website":"https://hospital.com",
  "contactEmail":"hr@hospital.com", "hospitalPhone":"+919876543210",

  "country":"India", "recruiterName":"Rahul Menon", "designation":"HR Manager",
  "businessEmail":"rahul@hospital.com", "recruiterPhone":"+919876543210" },
  "verification": { "status":"approved", "verifiedAt":"2026-09-20T12:00:00Z" },
  "hiringPreferences": { "specialties":[], "locations":[], "employmentTypes":[] } }

PATCH/recruiter/hospital-profile

Accept { "profile": { ...editableFields }, "hiringPreferences": { "specialties": [], "locations": [], "employmentTypes": [] } }. Do not accept changes to verification status, organization ownership, or approval. Return the updated envelope. Return 422 VALIDATION_ERROR with field errors for invalid values. Define whether changes to legal name, registration, or website trigger re-review.

{ "error": { "code":"VALIDATION_ERROR",
  "message":"Please correct the highlighted fields.",
  "fields": { "email":"Enter a valid email address." } } }
StatusMeaning / examples
400Malformed JSON or invalid request shape.
401Missing/expired token; invalid login/reset credentials.
403Wrong role, unverified email, pending/rejected organization, or unauthorized action.
404Resource unavailable or not visible to this organization.
409Email conflict, insufficient credits, or conflicting state.

12. Data Protection and Authorization Requirements

  • Candidate records, purchases, shortlists, payments, invoices, and hospital profile reads/writes must be organization-scoped server-side.
  • Keep personal candidate details, resume links, and contact information masked until an authorized unlock purchase is confirmed.
  • Verify organization approval at action time, especially candidate unlock and checkout.
  • Never accept a client-submitted credit balance, plan price, payment success flag, organization ID for access scope, or verification status as authoritative.
  • Make credit debits and payment webhook processing transactional and idempotent.
  • Use secure transport, password hashing, token expiry/revocation, rate limiting, audit events for sensitive actions, and redacted logs.

13. Frontend Integration Status and Known Gaps

Authentication: Current frontend register/login/OTP/recovery screens call shared auth API methods through recruiter-specific auth mapping. The pending/approved route decision depends on the backend returning the role, token, email verification, and organization verification fields defined here.
Workspace integration: Recruiter workspace screens now request data and actions through src/lib/recruiterApi.js, including GET and POST /recruiter/jobs for the Job Postings page. Recruiter sample records were removed; pages show loading, empty, or API error states instead of inventing records when an endpoint is unavailable. The proposed backend routes must be implemented and confirmed for the complete flow to run.

Checkout now redirects to a hosted payment provider and checks the backend session status on return. Payment success and credit changes must come from verified provider webhooks. Payment history and invoices display only backend records.
