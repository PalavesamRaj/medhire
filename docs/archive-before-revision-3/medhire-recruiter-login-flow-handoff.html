Recruiter Login
and Verification Flow

Backend contract for recruiter registration, email verification, sign in, organization review, protected hospital access, and password recovery.

Proposed API contract — backend confirmation required

Scope: This handoff covers recruiter authentication and the transition from verified email to pending organization review and approved recruiter access. Candidate and recruiter resource APIs are described separately in Recruiter API Handoff.
Project: MedHire
Document: Recruiter login flow handoff
Prepared: September 24, 2026
Frontend base: VITE_API_BASE_URL (defaults to /api)

1. End-to-End Flow

1. RegisterPOST /auth/register; create unverified recruiter; send email code.
2. Verify emailPOST /auth/verify-code; mark email verified.
3. Sign inPOST /auth/login; return role, session, and organization status.
4. Pending reviewPending or rejected organization cannot access recruiter resources.
5. Approved accessApproved status opens recruiter dashboard and hospital profile.
6. Recover accountForgot password → verify reset code → set a new password.

The browser can guide navigation, but the backend must enforce recruiter role, email verification, organization approval, and organization ownership on every protected request.

2. Common API and Security Rules

ItemRequirement
Base URLFrontend uses VITE_API_BASE_URL; endpoint paths below are relative to it. With the default value the login endpoint is /api/auth/login.
FormatJSON request and response bodies use application/json.
RolesCanonical role is exactly recruiter for recruiter registration, verification, and login.
EmailNormalize and compare case-insensitively. Use the same account identity across registration, OTP, resend, and login.
PasswordHash server-side; never return it or log it. Current frontend requires 8–72 characters with uppercase, number, and symbol.
Verification codeSix numeric digits, single-use, short-lived (about 10 minutes), and rate-limited for resend and attempts.
SessionReturn a short-lived access token. Prefer a Secure, HttpOnly refresh cookie; confirm refresh and revocation behavior with frontend.
Organization statusReturn organizationVerificationStatus on the user as pending, approved, or rejected. Keep this field authoritative and update it when review status changes.
AuthorizationVerify token, recruiter role, email verification, and organization approval on every recruiter resource endpoint. Never rely on React route guards for security.

6. Approval and Protected Recruiter Resources

When MedHire approves an organization, update its status in the source of truth. On the recruiter’s next login (or a future session-refresh/status endpoint), return the approved status. A stale browser session may continue to show pending until refreshed or reauthenticated; the backend must still enforce current approval on every resource request.

RequestRequired behavior
Pending/rejected recruiter calls recruiter data APIReturn 403 with stable code ORGANIZATION_NOT_APPROVED (or a distinct rejected code). Return no protected data.
Approved recruiter calls recruiter data APIAuthorize the recruiter and scope all reads/writes to their organization.
Missing, expired, or revoked tokenReturn 401; frontend must ask for login again.
Token belongs to candidate or another roleReturn 403; never expose recruiter information.

Dashboard, candidate search, shortlist, purchased profiles, plans/credits, checkout, payment history/invoices, and hospital profile contracts are in Recruiter API Handoff.

7. Password Recovery for Recruiters

The existing recovery endpoints are shared across roles. Preserve account identity and role through the recovery UI.

POST/auth/forgot-password

{ "email": "rahul@hospital.com" }

Return a generic 202 Accepted whether the email exists or not.

POST/auth/verify-code

{ "email": "rahul@hospital.com", "code": "482916", "purpose": "password_reset" }

Return a short-lived, single-use reset token. Do not treat a reset code as email registration verification.

POST/auth/reset-password

{ "email": "rahul@hospital.com", "resetToken": "reset-token-value", "newPassword": "NewExamplePassword@123" }

Invalidate the reset token and revoke other sessions as required. The confirmation password remains frontend-only.

8. Validation and Error Contract

Frontend validation improves usability; the backend must independently repeat all security and business validation. Return field-level errors in this shared envelope:

{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Please correct the highlighted fields.",
    "fields": { "email": "Enter a valid email address." }
  }
}
StatusMeaning
400 / 422Malformed data or field/business validation failure.
401Invalid credentials, expired session, or invalid reset token.
403Wrong role, unverified email, or organization not approved.
409Email already registered or conflicting account state.
429Login, verification, or resend rate limit reached.
500Unexpected server error; do not include secrets or stack traces.

Current browser checks include required recruiter identity/organization/location fields, email format, ten-digit phone input, strong password, matching confirmation, accepted terms, required login password, and six-digit numeric verification code.
