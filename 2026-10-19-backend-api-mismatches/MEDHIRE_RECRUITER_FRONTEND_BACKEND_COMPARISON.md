# MedHire recruiter frontend/backend API comparison

**Compared:** frontend source in this workspace against the user-pasted source-backed recruiter API examples and request/response matrix.

Protected recruiter calls use the frontend API base (default `/api`), so the frontend path `/recruiter/...` corresponds to the guide's `/api/recruiter/...`. The frontend sends the stored access token as a Bearer token. Example bodies below use redacted placeholders and are not captured runtime traces.

## Login and recruiter access

| Flow | Frontend request/expected response | Backend example in pasted guide | Difference |
| --- | --- | --- | --- |
| Login | `POST /api/auth/login`, JSON `{email,password,rememberMe}`. Frontend accepts a root object or `{data:...}` and needs `accessToken`, `user.role` (`recruiter`), optional `user.emailVerified`, and organization verification state on `user`. | The new matrix confirms required `email`/`password`, optional `rememberMe` defaulting false, and success response with duplicate root and `data` values including `accessToken`, `refreshToken`, and `user`. Recruiter role, email verification, and `organizationStatus` / `organizationVerificationStatus` are present. | **Matches.** Frontend's response normalizer supports both root and `data`; it accepts the documented organization status names and routes pending organizations to verification pending. |
| Auth gates | Recruiter pages call API after login with Bearer access token. | All recruiter calls require verified email, ACTIVE account, and linked organization. Verified-organization endpoints return gated errors otherwise. | **Response fields match.** The frontend recognizes the documented `organizationStatus` and `organizationVerificationStatus`. It does not pre-hide every verified-only page; gated endpoint errors remain the source of truth for restricted actions. |

## Specific corrections to the earlier mismatch notes

- Candidate search's query names and response aliases now agree with the pasted contract; do not report `maxExperience`, `licenseState`, `employment`, or `availability` as currently sent.
- The frontend now follows the requested locked-profile treatment: display professional fields clearly before unlock, mask contact values, and refetch detail after unlock for contact/resume fields. See [candidate profile display behavior](MEDHIRE_CANDIDATE_PROFILE_API_REQUIREMENTS.md).
- Hospital profile update previously sent unsupported keys. The frontend now sends only supported fields; organization type and recruiter/contact fields remain unavailable pending backend support.
- Team seat counts and pending invitations are explicitly absent from the documented GET response. The frontend now supports an expanded response; backend needs to provide those persisted values for them to appear.
- Checkout with `providerConfigured:false` and `checkoutUrl:null` is documented no-provider behavior, not an invalid backend URL. The frontend should explain provider unavailability.
- Active job edits are not supported by the backend contract. The frontend now prevents them and offers Close for active jobs; adding re-review requires a backend endpoint/contract change.

## Overall assessment

Remaining integration dependencies: backend support is needed for hospital organization/recruiter contact fields, a clickable invitation email URL targeting `/accept-invitation?token=...`, pending team invitations/organization seat usage in `GET /recruiter/team`, and active OWNER membership creation for recruiters registering a new organization so they can submit verification documents while its status is PENDING. Login, candidate search, checkout provider messaging, and active-job edit availability align with the supplied contract. Unlock includes the required idempotency header in supported secure browser contexts.
