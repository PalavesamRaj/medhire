# MedHire backend API mismatches

**Prepared:** 19 October 2026  
**For:** Backend team  
**Portals covered:** Authentication, Candidate, Recruiter, Admin

This handoff lists only unresolved API contract mismatches or flow gaps found while comparing the frontends with the supplied API documents. The source-verified contracts are treated as authoritative where they clarify earlier handoffs. Each item asks the backend team to confirm or change one concrete part of the contract.

## Authentication

| Priority | API / flow | Mismatch | Backend action needed |
| --- | --- | --- | --- |
| Blocker | `POST /auth/verify-code` -> `POST /auth/reset-password` | `reset-password` requires `resetToken`; the source-verified contract says production verification can omit the token. Without another grant, candidate, recruiter, and admin password resets cannot finish. | Specify one production flow: return a short-lived, single-use reset token; issue a documented reset-grant cookie; or add a grant exchange endpoint and update the reset request schema. Bind the grant to the verified email. |
| Flow unclear | `POST /auth/change-email` -> `POST /auth/change-email/confirm` | Production change-email omits the confirmation value, while confirmation requires `{token}`. The docs do not settle whether the email contains a code, link token, or code that must first go through `POST /auth/verify-code` with `purpose:"email_change"`. | Document the exact confirmation sequence and request body. Confirm the value delivered to the user can be submitted as `token` or identify the required exchange endpoint. |

## API failure status

**No endpoint has been verified as failing against the backend.** The frontend build and browser/unit test runs did not use a configured staging API with backend test accounts, so they cannot establish an HTTP status or response failure for any route.

The last recorded frontend checks were:

- `medhire-main`: production build passed; 21 unit tests passed; the custom Chrome browser check timed out connecting to Chrome DevTools at `Page.enable`.
- `adminportal2026`: production build passed; the recorded Playwright run had 15 passes and 27 UI/browser assertion failures. The admin repository handoff says those tests exercise demo/UI behavior and do not validate a backend. Admin source changes made after that run were build-checked but not rerun through the complete Playwright suite.

These are **frontend/test-runner results, not failed API calls**. To identify real API failures, please provide a reachable staging base URL, CORS configuration, test accounts for each role, and representative records. Then the endpoint families can be checked for actual request status and response shape.
