# MedHire recruiter backend API mismatches

**Prepared:** 19 October 2026  
**For:** Backend team  
**Portal covered:** Recruiter

This handoff contains only recruiter API mismatches from the combined mismatch document.

## Recruiter

| Priority | API / flow | Mismatch | Backend action needed |
| --- | --- | --- | --- |
| Dashboard DTO undefined | `GET /recruiter/dashboard` | The recruiter API reference says the response is service-defined and does not specify key names for search count, recommendation candidate fields, recent activity fields, or organization summary. The UI now maps common camelCase/snake_case fields and gets credits, purchased, and shortlisted totals from their documented endpoints; candidate-search count still depends on the dashboard payload. | Publish one dashboard response example/schema, including `candidateSearches`, organization identity/status, recommended candidate ID/name/specialty/location/experience, recent activity text/timestamp, and metric definitions. |
| Search result card data and filter behavior mismatch | `GET /recruiter/candidates` -> `GET /recruiter/candidates/{candidateId}` | The Find Candidates design cards expose initials, a professional title, specialty badge, verification badge, candidate ID, experience, location, education, license, availability, skill tags, and unlocked state. The frontend now maps `candidateId`, `currentJobTitle`, `yearsOfExperience`, `specialty`, `city`, and `state`, and sends only `query`, `specialty`, `location`, `minExperience`, and `openToWork` (plus pagination). It no longer sends `maxExperience`, `licenseState`, `employment`, or `availability`. Runtime screenshots show UUID profile URLs, generic/fallback titles, and limited details; experience filtering previously produced no matches when experience was unusable. The Figma result count (248) and card content are samples, not expected live values. | Return the agreed fields with accurate values, define the type/accepted values of `openToWork`, and return a stable candidate ID accepted by detail and shortlist routes; identify any separate UUID required for download. Confirm whether `minExperience` is a lower-bound filter and its units, how search query matching works, and whether combined supported filters use AND or OR. Return pagination metadata with `total` matching the active filters. The design also shows credential-verification, education, license, and tags; document/add these fields if they are intended to appear truthfully. |
| Candidate credential-verification badge undefined | `GET /recruiter/candidates` | The Find Candidates Figma shows a “Verified Credentials” badge on candidate cards. The documented search item has no credential-verification flag or status, so the frontend cannot determine when to display this badge truthfully. The current page therefore omits the badge unless the response supplies an explicit verification value. | Add a documented per-candidate `credentialsVerified` boolean or `credentialStatus` enum to the search item and detail candidate, and define which credentials/statuses qualify for the badge. Do not infer this badge from candidate profile completion or organization approval. |
| Candidate detail data missing or not renderable | `GET /recruiter/candidates/{candidateId}` | The latest profile screenshot shows “No professional summary,” no work history, no career preferences, and a skill rendered as `[object Object]`. The documented detail envelope includes `profile.summary`, `profile.skills`, `profile.workExperience`, and `profile.career`. The candidate profile handoff defines skills as `{ name }`, work history fields including `jobTitle`, `employerName`, `startMonth`/`startYear` and end dates, and career preferences as fields such as `employmentTypes`, `preferredLocations`, `shiftPreference`, and `expectedSalary`. Frontend mapping has been updated for these documented shapes, including object-valued skills and career-preference objects; `[object Object]` is a frontend rendering defect for the observed UI, not evidence by itself that the API omitted skills. | Return populated `summary`, `skills`, `workExperience`, and `career` values in the documented detail envelope for profiles that contain them. Confirm whether empty sections are genuinely unset or omitted by the API. Provide sanitized actual detail JSON for the candidate and the exact skill/career object shapes if they differ from `{ name }` and the documented profile envelope. Keep contact fields masked until unlock. |
| Applicant ID displayed as identity | `GET /recruiter/jobs/{jobId}/applications` | The screenshot displays a candidate UUID as the applicant's name. Candidate identity is masked until unlock; an identifier is not a display name. The UI now uses “Applicant” or masked initials and keeps the ID only for profile navigation/actions. | Include masked initials and available professional summary fields in each application item. Confirm the candidate ID accepted by the profile route. |
| Recruiter team response unavailable or incomplete | `GET /recruiter/team` | The Team page showed zero members and `0 / 0` seats. It assumed `data.items`, `seatsUsed`, and `seatsTotal`, so an alternate response envelope or missing values appeared as actual zero counts. The UI now unwraps `data`/`result`, accepts common team-list/seat aliases, and shows unavailable markers instead of false zero values when fields are absent. | Confirm the deployed route returns `{ items, seatsUsed, seatsTotal }` for the authenticated organization. Return an explicit empty `items: []` only when the team is actually empty and include numeric seat counts. Confirm `POST /recruiter/team/invitations` persists and delivers the invitation and returns its status. |
| Recruiter invitation acceptance flow incomplete | `POST /recruiter/team/invitations` -> invitation email -> acceptance -> `GET /recruiter/team` | The screenshot shows the email contains a standalone one-time token but no clickable acceptance URL. The frontend has no documented recruiter-invitation acceptance route, and after sending, the team response lacks the pending invitation and seat fields, so the UI reports `Invited (0)`. The current contract does not define how an invitee validates and consumes this token. | Define the recruiter invitation acceptance route(s) and payloads, including token validation, expiry, single use, and whether invitees must set a password or sign in. Include a clickable frontend acceptance URL in the email. Make `POST /recruiter/team/invitations` report the actual persisted/delivery status, and return the pending invitation in `GET /recruiter/team` with status `INVITED` plus the documented seat fields. Provide sanitized request/response examples and the expected acceptance URL format so the frontend can implement the flow.
| Plans response/catalog unavailable | `GET /recruiter/plans`, `GET /recruiter/credits` | The Plans & Credits screenshot shows no plan cards and a missing balance. The UI now accepts nested plans/balance envelopes and reports a missing list or balance field. If the documented `plans` array is empty, the backend has no available plans to render. | Confirm the endpoints return `{ plans, currentPlan }` and `{ available, used, currency }`, with an active plan catalog for the test organization. Provide sanitized endpoint responses. |
| Checkout response URL invalid | `POST /recruiter/checkout` | The checkout screenshot shows `Failed to construct 'URL': Invalid URL` after the plan loads. The UI now accepts common URL field aliases and requires an absolute HTTPS provider URL before redirecting. | Return the documented `{ checkoutSessionId, checkoutUrl }`, with `checkoutUrl` an absolute HTTPS URL. Provide the sanitized response body from the failing request. |
| Hospital profile fields not rendered | `GET /recruiter/hospital-profile` | The screenshot shows empty organization/contact fields, unavailable verification status, and blank hiring preferences without an API error. The UI now unwraps nested `data`/`result` responses and maps common organization, recruiter, address, verification, and preferences fields. | Confirm the endpoint returns `{ profile, verification, hiringPreferences }` for the authenticated organization. Provide one sanitized response matching the fields in the profile screen, including whether blank values are stored or omitted. |
| Hospital profile PATCH values not persisted/read back | `PATCH /recruiter/hospital-profile` -> `GET /recruiter/hospital-profile` | After editing organization type, registration number, contact details, and address, the UI's follow-up GET returned blank values for those fields. The frontend now displays the fresh GET as authoritative and warns when saved values differ. This proves a read-after-write mismatch in the observed session; it does not identify whether PATCH ignored values, persistence failed, or GET omitted them. | Confirm PATCH accepts and persists every documented editable field (`organizationType`, `registrationNumber`, `contactEmail`, `hospitalPhone`, `address`, `postal`, `country`, and profile contacts), especially for already-approved organizations. Return the updated `{ profile, verification, hiringPreferences }` envelope and ensure the next GET returns the same persisted values. If approved organizations cannot edit legal fields, return an explicit `403`/`409` or field-level `422` instead of silently ignoring them. |
| Fields underspecified | `POST/PATCH /recruiter/jobs` | Job writes accept numeric `salaryMin` and `salaryMax`, but the contract does not define currency or pay period. The UI also collects requirements separately, while the documented create fields do not clearly accept a structured requirements field. | Define salary currency/unit and whether requirements are a supported field or must be included in `description`. Apply the same fields to create, update, and detail responses. |
| Active job edit requires re-review | `PATCH /recruiter/jobs/{jobId}` | The running API returned “ACTIVE jobs cannot be edited by recruiters without a re-review flow.” The frontend now sends `status: PENDING_APPROVAL` for every edit of an active job and tells the recruiter it was submitted for review. The supplied handoff describes re-review for title, specialty, location, or salary changes; confirm whether all active edits require re-review or whether a separate endpoint is needed. | Support the documented PATCH transition to `PENDING_APPROVAL` while preserving existing applications, or document the required re-review endpoint and response. Return the updated job status so the UI can show the committed state. |
| Identifier mismatch | `GET /recruiter/candidates/{candidateId}/resumes/{resumeId}/download` | Candidate list/detail UI may use a public candidate ID; the protected download contract requires candidate and resume UUIDs scoped to the recruiter organization. | Identify the UUID field returned in recruiter list/detail DTOs and state whether detail/download paths accept public IDs or UUIDs only. |
